# Фоновая обработка и закупочные заказы

## Компоненты

- `main_ai.py` — постоянно работающий веб-интерфейс.
- Neon/PostgreSQL — заявки, результаты поиска, очередь и черновики заказов.
- `worker.py` — отдельный Render Background Worker.
- `job_queue.py` — долговечная очередь без дополнительного Redis.
- `procurement.py` — группировка включённых строк по поставщикам и ручное подтверждение.

## Безопасный запуск

1. Создать Background Worker из `render.yaml` и скопировать в него те же секреты базы и поставщиков.
2. Убедиться, что worker запущен и пишет `worker started`.
3. Только после этого добавить веб-сервису `BACKGROUND_QUEUE_ENABLED=true`.
4. Проверить одну тестовую заявку: статус должен пройти `queued` → `processing` → `ready_for_review`.

Если worker ещё не создан, переменная должна оставаться `false`: веб-приложение продолжит старую синхронную обработку.

## Заказы поставщикам

После проверки подбора кнопка «Сформировать черновики заказов поставщикам» создаёт отдельный черновик для каждого выбранного поставщика. Кнопка подтверждения переводит черновик в `approved_for_submission`, но пока не отправляет его наружу. Живую отправку можно включать только после реализации и проверки методов создания, статуса и отмены заказа конкретного поставщика.

## Прайсы и собственный каталог

`/dashboard/prices` принимает XLSX, XLS и CSV. Оператор выбирает лист, строку заголовков, соответствие столбцов, единицу цены и режим НДС. Оригинал файла, метаданные, версии и позиции сохраняются в общей базе. Новый полный прайс атомарно заменяет активную версию только того же поставщика и названия прайса. Некорректный импорт не отключает прежние цены; точные повторы не создают активных дубликатов. Один импорт — один выбранный лист, цены в RUB, до 12 МБ и 100 000 строк.

`/dashboard/catalog` хранит товары отдельно от наблюдений цен и фактов продаж: поставщик, закупочная и продажная цены, дата, число предложений по позиции (включая наше), способ поиска, URL и исходная заявка. Ручное добавление и новые цены сохраняют историю. Подтверждённая оператором продажа из `/dashboard/automation/jobs/{job_id}/catalog-sale` сохраняется один раз по заявке и позиции. Отправка предложения не является подтверждением продажи. Число предложений без цены/места среди конкурентов не доказывает ценовое преимущество.

`PriceListAdapter` и `OwnCatalogAdapter` участвуют в основном подборе и повторном поиске позиции. SQL-индексы по артикулам и словам отбирают ограниченный набор кандидатов без повторного чтения Excel или выгрузки всех прайсов. Затем применяются общие проверки бренда, размеров, типа товара и единицы цены. Цены сравниваются за единицу заявки; наличие из исторического источника не считается текущим подтверждением. Сохранённые счета/результаты не изменяются при обновлении каталога.

## Подготовка характеристик прайсов (22.10.2026)

`product_characteristics.py` извлекает ограниченный набор параметров по категориям с точным фрагментом исходного названия. Неизвестные категории и единицы требуют проверки. Служебные колонки и оформление листа не используются как характеристики товара. Это набор правил, а не универсальный разбор любых прайсов.

`prepared_catalog.py` хранит карточки отдельно от предложений версий прайса. Уникальный артикул связывает обновления только внутри того же каталога поставщика; дубли артикула и строки без артикула остаются отдельными. Товары разных поставщиков автоматически не сливаются по названию. Карточка хранит исходное описание, его хэш, версию правил, результаты и ручные исправления с журналом. Неизменившееся описание с устойчивым артикулом повторно не разбирается; при смене правил файл можно импортировать заново. Цена/остаток остаются наблюдениями из конкретной версии документа.

На странице проверки прайса есть отдельная форма «Подготовить каталог без подтверждения цены». Поддержаны ручное соответствие столбцов и четыре проверяемых шаблона (Сатурн, ИПК, Крепёжные системы, Уралпайп). Этот режим сохраняет числовую цену без предположения о валюте/НДС, допускает отсутствие цены, единицы и даты. Пустой остаток остаётся NULL, нулевой — нулём; «Под заказ» выделяется отдельно. Дата получения письма не является датой подтверждения остатков. Такие предложения не передаются в расчёт счёта. Обычный импорт подтверждённых цен сохраняет прежний контракт и дополняется характеристиками.

`/dashboard/prices/prepared` — поиск по индексированным словам, категории и параметрам до ограничения числа кандидатов; исходный Excel при поиске не читается. Известные конфликты исключаются; неизвестные значения не подтверждают совпадение. Надпись «Совпали выделенные параметры» относится только к распознанным требованиям, а не гарантирует полное соответствие. Неподдержанные категории дополнительно требуют сходства названия. Каталоги исторических/отключённых версий доступны по ссылке списка; в общем поиске участвуют только активные версии.

`/dashboard/prices/products/{id}` показывает происхождение, исходную строку и ручные исправления. `/dashboard/prices/match-order/{job_id}` запускает подбор для сохранённой реальной заявки (orderItems или items) без изменения заявки/счёта и без внешних запросов. Ссылка добавлена в просмотр заявки. Существующие API-адаптеры и ручной Sniper сохранены; автоматическое уточнение найденных SKU через API и автоматический запуск Sniper этим изменением не реализованы. Автоматический импорт почты также не включён.

Воспроизводимая проверка: `python scripts/validate_price_catalog.py --source-dir /path/to/archive --orders-json /path/to/snapshots.json --report /path/to/report.json` с предварительно выбранной тестовой базой через DATABASE_URL или AUTOMATION_DB_PATH. Скрипт загружает оригиналы через те же HTTP-обработчики приложения. Внешние документы, почтовые метаданные, снимки заявок и результаты не публикуются в git.

## Возможность поиска цен через ИИ

Текущий `ai_panel._call_openai` анализирует переданные данные без веб-поиска. Для отдельного поиска по сайтам подходит Responses API с инструментом `web_search`, ограничением `allowed_domains` на выбранных продавцов и сохранением ссылок-источников. Документация: https://developers.openai.com/api/docs/guides/tools-web-search . Этот внешний поиск пока не подключён.

Предлагаемый процесс: ручная кнопка по конкретной позиции → точный товар/характеристики и требуемое количество → поиск на выбранных сайтах → список предложений со ссылками → проверка совпадения, единицы/упаковки, НДС, количества, даты, доставки → сохранение проверенного предложения в каталог. Формулировка результата — «минимальная подтверждённая цена среди проверенных предложений», без гарантии минимальной цены во всём интернете. Закрытые B2B-цены и объёмные скидки запрашиваются через API/поставщика. Результат без проверяемой страницы и цены не попадает в счёт. Вводятся лимит стоимости/числа запросов, кэш и ручной запуск; ИИ используется для пробелов и неоднозначных позиций, а не вместо индексированного каталога.
# Sniper Search (2026-10-14)

Private panel: `/dashboard/sniper`; linked from the saved requests list and
request review. The user enters a Sniper PAT or logs in to issue one using
`POST /api/bff/v1/user/login` then `POST /api/v0/token/issue`. The login path in
the docs is relative to the site's BFF base; the actual base was verified in
the site's public frontend. Login/password whitespace normalization matches the
site. Rejected login responses expose only allowlisted reason codes (e.g. device
restriction, concurrent login, invalid credentials); arbitrary response text is
never displayed or logged. Login failures preserve the username and show an
inline alert with the HTTP status; secret fields are cleared and use separate
field names and autocomplete hints from the private panel login. An existing PAT is never
automatically revoked. The password is not stored; the PAT is Fernet encrypted
in PostgreSQL using a key derived from the stable application signing secret
(fallback: Zakupay API key). Changing that secret requires reconnecting Sniper.

Connection verification reads `/api/v0/requests/languages`, without search or
mail. New local drafts contain up to 20 goods and an optional saved request ID.
Only a second confirmed POST submits either `/api/v0/requests/scan` (contacts)
or `/api/v0/requests/wizard` (search plus mail). The wizard always searches for
its own recipients; it cannot mail a supplied exact recipient list. No pricing
adapter is added because contacts are not product prices or stock evidence.
Email/site exclusions are snapshotted into new drafts. Fractional quantities
are not rounded to fit Sniper's integer quantity field; include them in the
reviewed email body. Defaults are worldwide geography (ID 1), Russian (ID 1).

Durable compare-and-set submission state blocks double sends and all implicit
retries. Transport errors, invalid success responses, and upstream 5xx leave
an uncertain state requiring a check in Sniper's account. A crash after sending
also leaves the request blocked. State/results and the first 100 mailbox
replies refresh only on user action, with no automatic database/API polling.
Opening any Sniper page never starts a supplier search or sends mail. All
routes require the private panel session; POST actions also verify session-bound
CSRF tokens. API responses and credentials are never returned in error text.

## Сравнение предложений поставщиков

`/dashboard/automation/jobs/{job_id}/comparison` показывает матрицу сохранённых
предложений: строки заявки, столбцы поставщиков, несколько вариантов в ячейке.
Кнопки доступны из списка заявок и проверки подбора. Открытие страницы не запускает
поиск или опрос API. `supplier_comparison.py` сохраняет правила в `result_json`;
новых таблиц и миграций нет. POST защищён сессией, CSRF и проверкой версии результата.

Отказ от пары «характеристика — значение» относится ко всем поставщикам одной
позиции и действует на новые варианты после повторного поиска. Решение по
количеству относится только к конкретному предложению и сбрасывается при изменении
количества/единиц. Непроверенные отличия не участвуют в минимуме. Единицы приводятся
явным коэффициентом: известная конверсия, упаковка, длина изделия либо ручной ввод.
Переключатель «сумма / цена за единицу заявки» не изменяет коэффициент.

Выбор переносится в существующие проверку, счёт и закупочный черновик. При принятой
недопоставке в счёт переносится фактически выбранное количество, а исходная
потребность остаётся в `comparison_source`. Правила также проверяются в коммерческом
пути, чтобы старая форма не вернула отклонённый вариант. Отправленные/обрабатываемые
заявки и незавершённые отправки защищены от изменения. Скрипт не содержит опроса,
вызовов поставщиков или отправки сообщений. Доставка не добавляется к минимуму без
сохранённой подтверждённой стоимости; CSV включает причины исключения.

## Ускорение детерминированного подбора

`search_session.py` объединяет одновременные одинаковые обращения и повторно
использует успешный ответ только в пределах одного `build_vi_draft`. Ключ — тот же
экземпляр адаптера, точный текст запроса и лимит. Настройки региона, склада и
учётной записи принадлежат экземпляру адаптера. Другой запуск заново получает
ответы; сетевые ошибки не сохраняются для последующих обращений. Каждая позиция
получает независимую копию предложений: количества, проверки единиц, исключения и
решения сравнения рассчитываются отдельно. Список источников, варианты запросов
и пороги соответствия не сокращаются. `AUTO_REUSE_SEARCH=false` отключает
переиспользование для сравнительной диагностики.

История исключений загружается пакетно (один SELECT для обычной заявки до 400
строк), а не отдельным подключением на каждую строку. Новые отказы связаны с
заявкой, идентификатором строки (либо исходной позицией), названием, единицей и
исходным количеством. Старые записи, привязанные только к названию, остаются в
истории и не применяются автоматически к другим строкам. Изменение требований
сбрасывает область действия отказа. Правила таблицы сравнения хранятся отдельно.

Частичный поиск сохраняет исходные номера строк. При наличии `order_item_id`
перенос правил сравнения использует его, а не текущую последовательность строк;
для строк без ID действует исходная позиция и проверка неизменности потребности.
Не выбранные для повторного поиска строки сохраняют прежние результаты и решения,
если состав соответствующей исходной позиции не изменился.

В `result_json.search_metrics` и журнал записываются число фактических обращений,
переиспользований, ошибок, время подготовки, первого результата и всего подбора.
Эти счётчики не создают дополнительных записей в БД на каждое событие.
`python scripts/benchmark_draft_search.py --delay-ms 25` сравнивает заявки из
50 строк с 1, 10 и 50 уникальными названиями на одинаковых искусственных ответах.
Скрипт проверяет равенство результатов; его время не является замером живых API.
